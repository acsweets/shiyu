## 如何按节点开发

按 **00 → 01 → … → 14** 顺序推进。每个编号有一份主文档，任务与完成情况以该文档为准。

1. 开始一个节点时读取其前置文档，确认上一节点的产物、接口、测试和退出条件已经满足。
2. 实现“开发 TODO”，同步补齐“开发者验证 TODO”，保留可重复的演示/测试入口。
3. 你按“你需要检查的点”复核可见行为和结果，失败项写入该节点验收记录；不能只以代码完成替代功能通过。
4. 证据与结论齐全、没有阻断后，更新节点状态和本总览，再进入下一节点；后续发现问题回到所属节点补 TODO 与复测。
5. 本计划只定义工作，不在创建文档时执行开发或把待开发项目勾为完成。未测试的设备、平台和检查点保持未勾选。

“进入条件”只引用既有基线或上一节点交付物，不要求先实现后续节点。尚无正式 UI 时提供测试工具或临时演示入口；它不属于已交付的产品界面。

## 统一验证与证据约定

- 每份节点文档分别列出开发 TODO、你要检查的点、验证 TODO、交付物和完成条件；仅实际完成的项勾选。
- 当前 `scripts/check.ps1` 已包含 Flutter 格式/分析/启动测试与 Rust fmt/clippy/test；真实绑定和桌面系统调用通过 `scripts/check_m0.ps1` 执行。节点 02 的 Rust 业务黄金测试已接入；真实退休原生链路另执行 integration_test/retirement_test.dart。
- 时间测试固定 `now`、IANA 时区、设置和假日数据版本；共享黄金样例位于 `core/testdata/`；包含退休及节点 03 五类时间指标样例。
- 验收证据按节点存入 `docs/验收记录/<节点编号>/`，包含 commit、命令、系统/架构/SDK/设备、结果、截图或日志、已知问题与检查日期；需要形成决策时放入 `docs/决策记录/`。这些目录在产生真实内容时创建。
- 报告/截图不包含真实薪资、出生日期等个人敏感数据，使用合成验收数据。
- Windows 10/11、macOS 12/当前版本与 Intel/Apple Silicon、iOS 最低/当前版本、Android 最低/当前 API 分别记录。无硬件时明确待验证，不能以另一个平台或模拟器替代真机结论。
- P0（错误金额/隐私泄露/数据丢失/崩溃等）与 P1（核心流程/窗口/小组件关键能力失效等）必须解决后通过相应节点；发布要求 P0=0、P1=0。P2 保留复现、影响和后续安排。
- 节点记录可增加“负责人、预计起止、实际起止”；状态使用可开始/待开始/开发中/验证中/阻断/已完成，阻断说明缺少的外部条件和下一步，不伪报完成。
- 对外发布是节点 14 的后续执行动作，候选包验收通过不等于已上线。
